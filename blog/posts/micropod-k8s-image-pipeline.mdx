A local Kubernetes cluster lives or dies on its image story. kind has `kind load docker-image` — it exists because the same problem exists there: a registry pull that crosses a VM boundary you don't control is the slowest possible way to get bytes from your laptop into a node.

Micropod's version of the problem is sharper. Every container is a micro-VM on vmnet's NAT — and guest-side pulls through that NAT are *pathologically* slow, not just slow: the ~60MB MetalLB install took ~13 minutes through quay.io, and a 20MB pod image minutes more. Meanwhile the host's puller moves at wire speed.

So the cluster doesn't pull images. The host does — and pushes.

Four sources, one pipeline:

- **`k8s load myapp:dev`** — image already in Micropod's store? `container image save` writes the OCI archive locally, `container copy` pushes it into the VM, `ctr -n k8s.io images import` lands it in the cluster's containerd. No network at all.
- **`k8s load some.docker/image:tag`** — not in Micropod's store but in a *local Docker daemon's*? Probed over its socket (`$DOCKER_HOST`, Docker Desktop, colima, Lima) and `docker save`-ed straight into the cluster — images you already have in Docker move at disk speed.
- **`k8s load redis:alpine`** — nowhere local → the *host* puller fetches it, then the same inject path.
- **`k8s load ./bundle.tar`** — a `container image save` or `docker save` tarball injects directly. For remote callers, `LoadK8sImage` accepts the archive as bytes (`base64` in Connect JSON) — no local file needed.
- **`k8s images`** lists what's in the cluster's containerd.

```bash
$ micropod build -t myapp:dev .     # built on the host, APFS-native
$ micropod k8s load myapp:dev       # save → stream → import — ~0.5s for 4MB,
                                    # ~2.8s for a 273MB image
  ▸ injecting into micropod-k3s containerd
✓ loaded myapp:dev — reference it from a pod/deployment image: field
$ kubectl run app --image=myapp:dev --restart=Never
pod/app created          # Running immediately — zero pull
```

One subtlety worth knowing: kubelet resolves `myapp:dev` to `docker.io/library/myapp:dev`, while a bare `image save` keeps the short name — so the import is tagged with the fully-qualified ref automatically. Load `cachetest:2`, deploy `cachetest:2`, done. (That bug was found by a pod sitting in `ErrImagePull` with the image provably loaded — the tag mismatch is invisible until you know it's there.)

## Every surface, same op

The pipeline isn't a CLI-only trick — it's `LoadK8sImage` on the Connect API, streaming progress like `K8sUp` does:

The MCP tool means an agent's loop looks like: `k8s_load_image {ref: "redis:alpine"}` → `k8s_images` to confirm → workload manifest with `imagePullPolicy: IfNotPresent`. No pull-through proxy, no registry mirror, no `kind load` archaeology.

And because the k8s engine shares Micropod's image store with the Docker Engine shim, stock `docker` clients compose too: `docker build -t app:dev .` on the shim socket produces an image `k8s load` picks up with zero network, `docker save`/`docker load` work as expected, and `docker top`/`docker push` round out the surface. For API callers, one extra flag collapses build→cluster into a single request — `POST /build?t=app:dev&k8s=1` builds and injects; `POST /images/load?k8s=1` does the same for a tarball.

## Profiled, then made fast

The first version of this pipeline was honest but slow: `image save` → `container copy` → `ctr import` of a guest-side file. Profiling a 273MB image showed copy at ~57MB/s over vsock plus a second full read of the staged tar inside the guest — 11.5s end to end. The fix was to delete a hop: `container exec -i` forwards pipe stdin into the VM at ~170MB/s, so the archive now streams straight into `ctr images import -` with no file on either side. Two traps found along the way: a *regular file* as exec stdin is 10x slower than a pipe (the forwarder poller is pipe-shaped), and a fifo deadlocks entirely — so `loadImage` pumps the staged tar through a real pipe on a detached thread. `ctr import` still unpacks into the snapshotter — that ~3.5s on big images is guest CPU pod-start would otherwise pay later; keeping it here keeps `kubectl run` at ~1s.

Honest read: kind is marginally quicker per-op — its node is a container on the same Docker daemon, so "loading" is a `docker exec ctr import` with no VM boundary to cross, and its pod sandbox path is ~0.6s warmer. Minikube loses ~4x on the load stage. Micropod is the only one that works at all without Docker Desktop underneath, and the only one whose `load` *finds* an image wherever it lives — kind and minikube fail hard (`image: "x" not present locally`) when the ref isn't in the daemon's store. On a 13.6MB image the same shape holds: kind 1.2s / micropod 1.7s / minikube 5.6s.

## Iteration: a registry mirror on vmnet

`k8s load` streams a whole archive per reload — fine for one-shot deploys, wasteful for the inner loop. A **registry mirror** is the docker-daemon-like answer: `micropod k8s registry` runs a `registry:2` container on the host published on `:15000`, and `--registry-mirror http://192.168.64.1:15000` mounts a `registries.yaml` into the guest so its containerd consults the mirror *first* for every registry (fall-through to upstream on a miss). `micropod k8s push app:dev` tags into the mirror's docker.io-shaped path — pods then pull at vmnet speed, and repeat pushes move only changed layers.

Measured: a 4MB image pulled through the mirror in **316ms** vs ~16s upstream through the guest NAT (~50x), push → pull → pod Ready in ~1s warm. The honest trade vs `k8s load`: load guarantees the guest has the image with zero network; the mirror needs the registry running and a push per change — but it dedupes, which is what makes the docker-daemon model fast.

## Why this matters beyond speed

**Iterating on a workload** is `build → k8s load → kubectl rollout` — the loop kind users know, minus the Docker Desktop dependency and with the host's content store doing dedupe. The image that a pod runs is byte-identical to the one the host built, because it's the same archive.

**Offline/airgap workflows** — a tarball on disk is a complete input: `micropod k8s load ./images.tar` on a plane, or in a CI sandbox with no registry access.

**MetalLB itself** seeds through this path now: the two add-on images are pulled by the host puller and injected before the manifest applies — the install that took ~13 minutes of stalled guest pulls is a few seconds of local I/O.

**Determinism** — a cluster's image state is enumerable (`k8s images`) and writable (`k8s load`) through one API, which is what made the `ErrImagePull`-by-name-mismatch bug findable and fixable in the first place.
