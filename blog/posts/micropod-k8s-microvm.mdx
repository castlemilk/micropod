Every local-Kubernetes option on macOS pays the same tax: a Linux VM to host containers, then a cluster nested inside it. kind nests a k8s node inside a Docker container inside Docker Desktop's VM. colima nests it inside a Lima VM. The nesting is where the overhead and the networking weirdness come from — a kind `LoadBalancer` service can never get an IP your Mac can actually route to, because the whole topology lives behind Docker's VM NAT.

Micropod's container model removes a layer: every container **is** a micro-VM with its own kernel on Apple's vmnet shared network. Kubernetes doesn't need to be nested at all — `k3s server` can just be a VM's workload.

## One VM, whole cluster

```bash
micropod k8s enable   # opt-in; writes a small config file
micropod k8s up       # ~21s to a Ready node, image cached
export KUBECONFIG=~/.micropod/k8s/kubeconfig
kubectl get nodes
# NAME           Ready   control-plane   v1.34.1+k3s1
```

Inside the VM, `k3s server` brings up etcd, the apiserver, scheduler, controller-manager, kubelet, and its own containerd — the usual k3s all-in-one layout. From the host you see a single container entry; from `kubectl` you see a fully working cluster with coredns, metrics-server, and local-path-provisioner running.

The VM gets a real address on the vmnet subnet (`192.168.64.x/24` on this machine). The apiserver's TLS SANs already cover it, so the host kubeconfig is the in-VM kubeconfig with one string rewritten — `127.0.0.1` to the VM address.

## MetalLB: the part kind can't do

`k8s up` installs MetalLB v0.14.9 and hands it the tail of the VM's subnet (`x.x.x.240–250`, override with `--lb-pool`). Because the VM sits on vmnet as a real L2 peer, MetalLB's ARP announcements reach the Mac directly — `type: LoadBalancer` services get IPs you can curl:

```
$ kubectl expose deploy web --type=LoadBalancer --port=80
$ kubectl get svc web
web   LoadBalancer   10.43.68.246   192.168.64.240   80:31224/TCP
$ curl http://192.168.64.240/        # HTTP 200, ~3ms from the host
```

On kind this ends at `<pending>` — the LoadBalancer type doesn't resolve at all unless you bolt on MetalLB yourself, and even then the IPs live inside Docker's VM where the host can't reach them without a user-space tunnel. We consider this the headline difference, not the boot time.

Traefik stays installed for `Ingress` resources on the node address (disable with `--no-ingress`), and servicelb is always off so MetalLB owns the type cleanly.

## Programmable from every surface

The engine isn't just a CLI trick — it's a first-class API. `K8sService` joins the Connect surface (typed in the Go, TS, and Swift SDKs), REST aliases land under `/v1/k8s/*`, and six MCP tools (`k8s_enable`, `k8s_up`, `k8s_down`, `k8s_status`, `k8s_kubeconfig`, `k8s_disable`) mean an agent can spin a cluster without knowing any of this exists:

## Measured against kind

Same MacBook, both runtimes warm, workload images cached on both sides. `micropod k8s up` measured end-to-end including API-ready wait and kubeconfig write; `kind create cluster` measured the same way. The losses are reported first because they're real.

Where kind wins: single-pod launch (~0.6s vs our ~1.1s). The gap isn't vCPUs — bumping the guest to 4 didn't move it; it's kind's pod-sandbox path inside an already-warm Docker VM. Where it loses everything else: the network. Our VM is a real vmnet peer, so service traffic crosses one bridge hop — kind's can't reach the host at all without `kubectl port-forward` or a tunnel, and its ingress story starts with extra plumbing ours doesn't need.

## The slow path: image pulls

The one genuinely bad number in profiling wasn't in the table because we fixed it during the profiling. Image pulls through the guest's vmnet NAT are pathological — a ~60MB MetalLB install took ~13 minutes from quay.io, and a 20MB pod image minutes more. Docker's puller doesn't have this problem.

The fix is architectural, and it's why MetalLB works well here: `k8s up` now pulls add-on images with the host puller, then injects the OCI archive straight into k3s's containerd — `container image save` → `container copy` → `ctr -n k8s.io images import`. Seconds, not minutes, and idempotent on reruns. It also means the MetalLB install is deterministic enough to pin and test.

Micropod's ~700 MB is the whole thing: kernel, k3s, and pods included. (The hypervisor process itself reserves the configured guest RAM, ~1.8GB RSS on the host for a 1GB guest — Apple's VZ doesn't balloon that down, which is the honest ceiling on the "tiny" claim.)

## Caveats worth stating

- **Single-node by design.** One VM is one node — this is the cheap local-cluster story, not multi-node scheduling.
- **Privileged guest.** The VM runs with `--cap-add ALL` and the runtime's read-only procfs paths cleared — kubelet writes `/proc/sys/kernel/panic` on boot and dies without it. It's still a hardware VM boundary, but treat the guest as trusted.
- **Pod images still pull through the guest.** Seed-by-host applies to the add-ons Micropod installs (MetalLB today); a workload `image:` you reference still pulls over guest NAT the first time. Pre-seeding workload images via the same path is the obvious next step.
- **State lives in the VM.** `k8s down` removes it — etcd, images, everything. Ephemeral is the point; persistent clusters are a different tool's job.
