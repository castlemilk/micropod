## Methodology

`scripts/bench_shim_vs_docker.py` drives both daemons through their Docker-compatible sockets — Micropod on `unix://~/.micropod/docker.sock`, Docker Desktop on `unix:///var/run/docker.sock`. Identical request sequences, warm caches, no cold-start pollution (the cold-start numbers are measured separately and are equally unflattering to a heavyweight VM — 169 MB versus 1.24 GB at idle includes everything).

The big multipliers are honest but need the caveat attached: list and image reads are served from a read-through cache with a 1 s TTL bound, so they're effectively `memcpy` of an encoded body. Docker Desktop's `images/json` walks its storage layer every call. The cache is a real engineering choice with real guardrails (reads only; mutations always resolve fresh) — it's covered in detail in [the optimizations post](/micropod/blog/micropod-optimizations/). The uncached paths matter too: `inspect` at 0.5 ms is a genuine in-process lookup, not a spawn.

`system df` is the outlier worth a sentence: Docker Desktop takes nine seconds because its `df` walks the overlay filesystem inside its VM; Micropod joins three cached lists in-process.

The headline number holds up: a complete create→start→exec→logs→stop→rm roundtrip is 2.7x faster, and it's dominated by `stop`. Docker Desktop honors the full 2-second grace period waiting for a SIGTERM handshake that a naive `sleep`-PID-1 container will never answer. Micropod's shim executes stop as the runtime's atomic instant-stop — which is also the honest way to treat a runtime where SIGTERM delivery to PID 1 is unreliable anyway.

## The honest losses

`start` at 529 vs 70 ms is the structural gap, and it isn't shim overhead — it's the price of the isolation model. Docker Desktop's `start` is a process spawn inside one warm, shared Linux VM. Micropod's `start` is a real micro-VM: VM create, kernel boot, DHCP lease, virtiofs rootfs attach, init. That ~0.5–1.0 s is the floor of actually giving every container its own kernel.

`exec`, `logs`, `rm` at ~30–75 ms each pay ~1 CLI spawn (~15–80 ms measured per `Process` invocation into `container-apiserver`). That's a structural floor unless a persistent apiserver session replaces per-call spawns — it's on the backlog.

**10x concurrent lifecycles: 6.5–9 s vs 2.62 s** is the loss that matters most for CI fleets. Ten parallel VM boots contend for CPU — boots are compute-bound and degrade under machine load. If you're sizing a fleet, physical cores ÷ 2 is the sane concurrency default, and pre-pulling the image matrix removes the network from the equation entirely.

Docker Desktop idles at 7.4x the memory — and the Micropod number is deliberately conservative: it counts the shared Apple `containermanagerd` and apiserver processes plus a running alpine VM, not just Micropod's own ~30 MB of helpers. On a 16 GB laptop running an IDE, a browser, and a simulator, that's a gigabyte you get back.

## Where that leaves you

If your workload is API-shaped — dashboards, agents polling state, testcontainers spinning databases per suite — Micropod is strictly faster and much lighter. If your workload is many parallel cold starts, Docker's shared-VM model wins today, and closing that gap means warm-start work (keep-alive machines already exec at ~0.1 s) rather than pretending the boot doesn't exist.

Reproduce it yourself:

```sh
$ python3 scripts/bench_shim_vs_docker.py unix:///~/.micropod/docker.sock shim --json bench/shim.json

$ python3 scripts/bench_shim_vs_docker.py unix:///var/run/docker.sock docker --json bench/docker.json

$ bash scripts/bench_runtime.sh idle    # RSS sums — intrusive, stops both runtimes
```

<Callout title="guardrail">
`--baseline bench/shim.json` fails the bench if any p50 regresses more than 20% against a saved run — the numbers above can't quietly rot.
</Callout>
