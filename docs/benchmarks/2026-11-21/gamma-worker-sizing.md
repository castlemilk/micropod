## VM size and container limits

The new CLI on Gamma returned `{"count":6,"source":"hw.perflevel0.physicalcpu"}` for `MICROPOD_CI_CPUS=auto`, and four for the fixed control. This 18-core M5 Max has six Super cores and twelve Performance cores. The policy sizes the VM from the fastest tier. macOS chooses where its vCPUs actually run. The result is bounded by active CPUs and Virtualization.framework's limits. An unavailable tier count falls back to four within those bounds. Linux CPU quotas are independent. [Apple processor topology](https://developer.apple.com/documentation/kernel/1387446-sysctlbyname/determining_system_capabilities) · [VM configuration](https://developer.apple.com/documentation/virtualization/vzvirtualmachineconfiguration)

For the throughput experiment use the independent Interactive launchd role for both Micropod workers. Provision separate benchmark directories and sockets. Keep both Micropod workers on the same binary, Linux image, Reno route, direct macvlan path and fixed 512 KiB relay. Use four vCPUs for the baseline, six for the candidate and six for OrbStack. Configure all VMs with 4 GiB, keep each test container capped at four CPUs, and preload the same ARM64 netbench image on each engine. The production CLI supports one registered worker per account. The existing Gamma experiments used distinct launchd job labels for isolated benchmark workers.

```sh
    BENCH_OFFERED_CLIENT=/tmp/mp-offered bash scripts/bench_published_ports.sh "$RESULTS_DIR"
```

Export `BASELINE_HOST`, `CANDIDATE_HOST` and `ORBSTACK_HOST` as the three local Docker endpoints and `BENCH_GUEST_PROBE_DIR` as a directory shareable at the same absolute path on each worker. Set `RESULTS_DIR` to a new directory. The harness checks distinct engine identities, VM vCPU counts, image configuration and rootfs hashes, and in-container CPU, memory and PID limits. Each engine gets three warm-ups. Each scored round offers 240 fresh connections over six seconds alongside 32 bulk streams. The six possible engine orders rotate. A failed identity request, a lost stream or a reopened connection invalidates the round. Raw failures and their round numbers remain in the results.

`offered-summary.json` reports the six-versus-four Micropod effect separately from the equal-size peer comparison. Report latency and every failed round alongside throughput. The Gamma release criterion requires clean Micropod rounds and the lower paired interval above parity before claiming a repeatable bandwidth win. Use a separate trace run for effective priority, tier residence and runnable wait. A new six-vCPU head-to-head remains unmeasured. ## Guest scheduling

The installed 7.3.5 image has BTF and CFS bandwidth support. Its config disables `SCHED_CLASS_EXT`. The optional `full-scx` build profile uses full preemption, enables sched_ext and its cgroup hooks, and verifies the generated config before building. Use the pinned archive and Apple base config with `ci/build-worker-kernel.sh ARCHIVE APPLE_CONFIG OUT full-scx` on ARM64 Linux. Choosing the kernel profile leaves Linux’s fair scheduler active until a policy is explicitly attached. [Linux sched_ext](https://docs.kernel.org/scheduler/sched-ext.html)

On a disposable native worker with matching guest tools, run `python3 scripts/check_worker_cpu_quota.py "$ENDPOINT" fair`. Repeat with the exact active ops name after loading the candidate policy, and again with `fair` after unloading it. The check compares two live job cgroup paths from the worker, verifies that the leaves share an immediate parent, checks membership of the busy tasks under sched_ext, and measures consumed CPU time at two CPUs, half a CPU, then two CPUs. It also checks the memory and PID limits. Kernel metrics expose the scheduler state, ops name and enable sequence. A policy can leave the value in `cpu.max` intact while failing to enforce bandwidth. Preserve these measurements before comparing p95 or changing the worker's cgroup layout. [Kernel bandwidth discussion](https://lists.openwall.net/linux-kernel/2026/08/18/1361)

## Warm CI and disks

`MICROPOD_CI_POSTGRES_PATH=bridge bash ci/worker-pipeline.sh all "$ENDPOINT"` creates a guest bridge just for this pipeline. The SQL client connects by service name, creates a table, inserts a row and reads it back. Both containers and the network are removed at exit. The client has no runtime socket mount and PostgreSQL has no published Mac port. Keep identical images, cache state and SQL work on both engines when comparing wall times. The earlier Testcontainers pipeline measured 5.65 s for an edited Micropod run and 22.55 s for OrbStack, with unchanged reruns of 3.28 s and 8.73 s. The new bridge path has yet to produce a live timing. [Full CI measurements](../2026-11-20/full-ci.md)

On Gamma's APFS volume, a 512 MiB raw fixture containing 32 MiB of data took a median **0.189 ms** to clone across 16 clones. The first private 4 KiB write and fsync took **28.9 ms**. Each sibling retained its own marker and the base retained the original. This measures the disk primitive. It excludes guest boot, ext4 recovery, database startup and package builds. Reproduce it with `python3 scripts/bench_worker_clone.py DIRECTORY_ON_APFS`. [Raw samples](gamma-worker-sizing.json)

Gamma runs macOS 26.5.1. macOS 26 supports ASIF images. DiskImageKit's stacked writable overlays and Virtualization.framework custom virtio devices arrive in macOS 27. On a 27 rig, compare a writable ASIF layer over an immutable base against the same APFS clone with identical guest bytes. Measure first write, fsync, private allocation, warm pipeline wall time, base integrity and restart recovery. If published TCP still limits a target workload after VM sizing, prototype one VZ custom device on that rig before committing to a replacement VMM. [Apple storage attachments](https://developer.apple.com/documentation/virtualization/vzdiskimagestoragedeviceattachment) · [Apple overlays and custom virtio devices](https://developer.apple.com/videos/play/wwdc2026/224/)

OrbStack documents its shared kernel, dynamic VirtioFS caching, custom network stack and Apple Silicon syscall optimization. Its developer also describes a custom Rust virtualization stack. These explain which subsystems are worth profiling. Their contribution to Gamma's bandwidth gap remains unmeasured. This comparison uses Micropod's existing guest mitigations. [OrbStack architecture](https://docs.orbstack.dev/architecture) · [Developer description](https://news.ycombinator.com/item?id=48470145)

ArcBox publishes a 52 Gbit/s host-to-container TCP result using iperf3. Its table identifies Docker Desktop as the 44 Gbit/s comparator. A direct comparison on Gamma would use the same port direction, resource limits, simultaneous downloads and fresh-connection load as the Micropod run. [ArcBox measurements](https://arcbox.dev/docs/core/benchmarks)
