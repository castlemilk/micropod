# Where warm CI spends time on Apple Silicon

**The first experiment after Gamma is released should put each job's mutable checkout on its own guest ext4 volume.** The control writes the same files under the same `/job` path on Docker's overlay. Charge volume creation and deletion to the candidate. Both arms keep the same persistent kernel, toolchain and scoped package caches. This can isolate workspace cost in a Go/npm edit. The Alpine launch control separately measures how much time is spent getting even a tiny process running.

The fixture is pinned to the warm-CI comparison source `06bfc10ba545ed6a276a21e9b1dd371c00925448`, on top of warm-worker revision `5376e95c`. Go and Node sample tree IDs are `b3fea27163f5da4ad1f5f13b66fae8c62dedf572` and `753ce95bb2969ea50a80d6282bb674f0fb46737c`. The original three-arm Alpine harness still hashes to `77c3b71e40d2667866c8fd81368d56d39c0fa40109c32ba3f067ff3b1e538791`. The older Micropod `ci run` versus OrbStack `docker run --rm` series measures native-path CI performance. PostgreSQL at `2ef1bc4` remains a separate compatibility workload. ## What reproduced locally

Five serial macOS ARM64 checkouts ran real Go tests with test-result caching disabled, an HTTP handler assertion covering status, body and revision, all three original Node tests, the npm build and the CLI output check. The edit changed reachable Go and Node behavior. A fresh repeat invoked the Go application linker once. Restoring a verified exact product reduced that to **zero**. Truncating the stored object triggered a normal rebuild with **one** link and the identical SHA-256. A source, compiler, target or scope mismatch and an unfinished publication were checked. Five of five runs passed on the first attempt. This tests a private producer and consumer on one host. Worker-crash recovery, concurrent readers and elapsed Linux speedup still need evidence. [Full functional receipt](host-cache-replay.json) · [Runnable replay](../../../../scripts/verify_warm_edit.py)

There was one offline import of the lock-pinned 2,625-byte npm package and four subsequent verified hits, **10,500 logical hit bytes**. On the fresh repeat, Go named 220 preexisting build-cache objects with **126,673,108 logical bytes** across the test/build traces. This is a lower bound on referenced preexisting object bytes. It does not measure physical reads or bytes saved. The host used a private warm Go seed, Go 1.27.2, Node 24.22.2 and npm 11.19.1. The Linux tool image must independently report its actual versions. The selected main Go package imports the standard library, so a zero external module-cache hit count is legitimate. [Go build cache](https://pkg.go.dev/cmd/go#hdr-Build_and_test_caching) · [npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/) · [npm cache integrity](https://docs.npmjs.com/cli/v11/commands/npm-cache/)

## Candidate decisions

| Candidate and availability | Largest plausible saving | Measurement and falsifier | Rollback |
| --- | --- | --- | --- |
| **1 · Private ext4 workspace.** Supported by current stock Docker. Use a fresh `volume-nocopy` checkout per job. Package stores stay in the same locations on both arms. | Mutable source, output and `node_modules` metadata, writeback and overlay bookkeeping inside a job. Container creation common to both arms still costs time. | Compare cold/edit/repeat net batch and client p50/p95 at 1 and 16. Charge Docker volume create/rm and source copy. Record container-only time, effective mounts, writes and PSI. Drop the candidate if volume management consumes the gain, the paired signs vary by order, or isolation, first attempts or concurrent tails regress. | Remove the job mount. The harness deletes only its labelled volumes and containers. [Docker volume behavior](https://docs.docker.com/engine/storage/volumes/) |
| **2 · Immutable build products with publication on demand.** The exact-source Go preparer and guest OCI exporter already exist. The extension would let authorized jobs lease a verified toolchain/target product before constructing a new source-specific image. | Repeated linking or installing, manifest registration and duplicated unpacked snapshots. Five archival revisions each sent only 13,824 metadata bytes and zero new blob bytes, yet six unpacked suite snapshots used 76,406,784 bytes. An alternate ordering used 14,356,480 bytes in that experiment. | Compare exact repeats, reachable edits and unrelated edits. Record links, cache hits/bytes, hash/restore cost, publisher wait, first consumer read, unpacked allocation and resources retained after GC. Reject on stale output, cross-scope access, corruption uptake, lost offline recovery or a slower end-to-end first consumer. | Use the existing source-only compile and synchronous image publisher. Keep an in-use generation leased until the reader exits. [Existing preparer](../../../../ci/prepare-go-workspace.sh) · [Measured OCI publication](../../2026-11-20/go-suite-layers.md) · [OCI ChainID](https://github.com/opencontainers/image-spec/blob/v1.1.1/config.md#layer-chainid) |
| **3 · A version-gated disk stack per worker generation.** DiskImageKit requires **macOS 27**. Standalone ASIF arrived in 26. A raw base can have ASIF upper layers. The measured Mac ran 26.5.1. | Worker provisioning, reset and duplicate fixed disk contents between generations. A persistent warm worker boots once, so per-container launch cannot save another disk clone. | On a separate supported Mac, compare raw ext4 on APFS, an APFS clone and an immutable base with a private writable ASIF layer. Measure open, first write, fsync p95, mixed reads, physical growth, durable reopen and interrupted publication. Falsified if the write/flush tail or retained space erases setup gains. | Reopen the prior raw disk through the existing VZ attachment. Use one writable ext4 owner and one active kernel per worker. Other future VM APIs require their own SDK and OS checks. [Apple DiskImageKit and VZ](https://developer.apple.com/videos/play/wwdc2026/224/?time=735) · [Current VZ disk attachment](https://developer.apple.com/documentation/virtualization/vzdiskimagestoragedeviceattachment) |

For option 2, the publication key must cover the repository and producer trust scope, complete reachable inputs and lockfiles, immutable tool image, actual compiler/linker or Node ABI, target, CPU features, build flags and output contract. The replay covers a single pure-Go package with CGO off. Native extensions, C headers, libc and install scripts require additional inputs or a miss. Jobs retain private writable workspaces and their own test executions. Publish verified immutable blobs first, then atomically expose the manifest. An incomplete producer, eviction or bad digest must leave the source build usable. The BuildKit v0.35.1 reference provides shared, private and locked cache mounts. Cache mounts can be collected and carry no correctness guarantee. The OCI descriptor authenticates bytes against an expected digest. Producer authorization is a separate check. ## Kernel and storage checks that could change the decision

The installed Apple guest kernel is `vmlinux-6.18.35-197`. Its embedded config hashes to `a5dfc1ee37dcd4bc6d727e4de617bc45a40cf32e7ebc52fb6f0472c8fbf60c21`. The worker source passes `psi=1` because the compiled default disables PSI. ext4, virtiofs, overlayfs, CPU sets, fair group scheduling, cgroup writeback and tracepoints are present. `SCHEDSTATS`, `sched_ext`, BFQ, io.cost and io.latency are absent. MGLRU is compiled with its default off. Verify the real boot ID, release, command line, cgroup files, live MGLRU bitmask and effective mount options in the receipt. [Embedded configuration](worker-preflight.json) · [VM construction](../../../../Sources/MicropodRuntime/SandboxVM.swift) · [Apple guest kernel source](https://github.com/apple/containerization/blob/main/kernel/README.md)

| Investigation | Availability and possible cost | Observable result that would rule it out | Revert or fallback |
| --- | --- | --- | --- |
| CPU placement and reclaim | Keep one CPU per job, all four guest CPUs available and ordinary CPU weights. Compare per-job effective cpuset, CPU time, throttle, CPU PSI, batch time and tail fairness. `memory.current`, `memory.events`, file refaults, scan/steal, major faults, dirty/writeback and memory PSI distinguish eviction from CPU backlog. Existing native scheduling results make static pinning a low priority. | Little runnable pressure, or worse tail under equal-budget placement. Little memory PSI and few refaults argue against reclaim work. Guest affinity supplies no Apple P/E-core placement evidence. | Omit per-job affinity on a disposable comparison. Leave reclaim, scheduler and sysctl settings as configured. [cgroup v2](https://docs.kernel.org/6.18/admin-guide/cgroup-v2.html) · [EEVDF](https://docs.kernel.org/scheduler/sched-eevdf.html) · [PSI](https://docs.kernel.org/accounting/psi.html) · [MGLRU](https://docs.kernel.org/admin-guide/mm/multigen_lru.html) |
| Filesystem path and lower-file copy-up | The configured host share enters at its Mac path through virtiofs. Guest volumes live on ext4. Writes to a preexisting image file can copy data up even with metadata-only copy-up available. New checkout files are created in the upper layer on the baseline. | Compare identical paths and operations. A separate disposable toolchain container reads or rewrites the same 4 KiB of an immutable lower file. Record unchanged content hash, Docker diff and total SizeRw growth outside application timing. A delta for this probe gives no measurement of bytes copied by an application job. Lack of a net workspace win rules out this optimization for the tested loop. | Discard the labelled job and private directory. Keep ext4 journaling and mount settings. [OverlayFS behavior](https://docs.kernel.org/filesystems/overlayfs.html#metadata-only-copy-up) · [Copy-up source](https://github.com/torvalds/linux/blob/master/fs/overlayfs/copy_up.c) · [ext4](https://docs.kernel.org/admin-guide/ext4.html) |
| Lazy pulls and CI publication | BuildKit cache export and containerd's eStargz snapshotter are available upstream. Probe snapshotter support separately. Lazy pulls could remove cold transfer/unpack from initial launch and move fetches into execution. The preloaded Alpine control uses zero registry traffic. | Compare end-to-end first and second consumer, fetched/compressed bytes, digest checks, offline behavior, publication CPU, first-file fault latency and GC. Zero fetched bytes on the target path or a slower first verified result falsifies the claim. | Keep eager local OCI content, normal unpack and synchronous export. Research this only on disposable infrastructure. [BuildKit exporters](https://github.com/moby/buildkit/blob/v0.35.1/README.md#cache) · [eStargz snapshotter](https://github.com/containerd/stargz-snapshotter) · [OCI layers](https://github.com/opencontainers/image-spec/blob/v1.1.1/layer.md) |

On APFS, 16 previous clones of a 512 MiB sparse file with 32 MiB populated gave **0.189 ms** median clone time and **28.885 ms** median first private 4 KiB write plus ordinary fsync (21.911–51.614 ms). Base and sibling markers survived. The second number includes the flush. The archive lacks matched ext4 and virtiofs measurements. The new path probe pairs clone and ordinary private files, separates first/repeat pwrite from fsync, and times a 32 MiB buffered read, an 8 MiB sequential write and 128 create/stat/rename/unlink sets. It records unsupported FICLONE as unavailable. Logical allocation in `st_blocks` cannot identify private APFS extents. ## Exact local reproduction

In a fresh directory use `git clone --branch perf/warm-edit-cache-research-20261122 --single-branch https://github.com/castlemilk/micropod.git` and enter that checkout. The read-only preflight returns 1 when the session/socket is missing. The host replay uses a locally staged `picocolors@1.1.1` tarball and verifies its SHA-512 against the pinned npm lock. Omit `--npm-tarball` if that payload is already in the local npm content store. Existing host tools must include Go, Node, npm and Python 3.9+. These commands perform no registry or CI work. [Pinned npm origin](https://registry.npmjs.org/picocolors/-/picocolors-1.1.1.tgz) · [Fixture source](../../../../ci/samples)

```sh
out=$(mktemp -d)
python3 -B scripts/test_bench_docker_launch.py
python3 -B scripts/test_warm_edit_profile.py
python3 -B scripts/profile_warm_edit.py inspect --clients 1 16 --blocks 6 --output "$out/preflight.json"
python3 -B scripts/verify_warm_edit.py --npm-tarball "$TARBALL" --output "$out/host.json"
```

Use the following zsh/bash commands **after the TCP owner releases the dedicated slot**, with the worker already running and idle. `TARBALL` is the staged tarball. `MICROPOD_BIN` is the existing CLI capable of reading this worker's status. `WORKER_BUILD_RECEIPT` is an existing trusted build record containing `source_revision` (the full `06bfc10…` SHA above) and `worker_executable_sha256`. The driver checks the active supervisor's executable vnode and hash. Without that provenance a run is labelled unattested. The native ARM64 tool image must be locally available with OCI config `sha256:73e5c74172d3555c685f3c8aad44163b52893478974e4c9926ba16a8a2c3a350`. The default local image ID is `sha256:ebc2079e1a616bf43ca219e21b53d9bac7043e71d3e2f68eebdaa8c26fed4ded`. The pinned Alpine must also be preloaded. Endpoints and budgets are inspected before any timing. [Driver and admission checks](../../../../scripts/profile_warm_edit.py)

```sh
common=(--slot-released --worker-home "$HOME/.micropod/ci"
        --docker "$(command -v docker)" --micropod "$MICROPOD_BIN"
        --npm-tarball "$TARBALL" --build-receipt "$WORKER_BUILD_RECEIPT")
python3 -B scripts/profile_warm_edit.py run "${common[@]}" \
  --clients 1 --blocks 1 --output "$out/smoke.json" &&
python3 -B scripts/profile_warm_edit.py run "${common[@]}" \
  --clients 1 16 --blocks 6 --seed 20261122 --storage-probes --output "$out/paired.json"
python3 -B scripts/ci_benchmark_store.py warm-edit-profile "$out/paired.json" \
  --database "$out/measurements.sqlite3"
```

Pass `--workspace-parent "$EXISTING_CONFIGURED_DIR"` to the second invocation to include a temporary directory within an already authorized virtiofs share. The harness verifies its effective filesystem from inside the job. Without such a share it leaves that path unmeasured. One Micropod-only Alpine warmup and one unscored diagnostic per width reuse the original fixture, stock executable, verified native config, one CPU, 256 MiB, disabled network, no pull, checked streams and exit 23. The three-arm comparison has its own unchanged reproduction above.

The edit schedule pairs storage arms in alternating order and rotates widths across six blocks. A fresh, initially empty scoped package store is created for each arm/block/width. The image and VM stay warm. Cold means cold package stores, with trusted offline inputs already present. The job runs revision A, reachable edit B and then B again in three fresh checkouts. At width 16 the jobs contend for the same scoped package cache. Each gets one CPU and 1 GiB, network off, fresh tests and a verified product. Pair eligibility requires matching outputs, both arms successful and host idle within five percentage points, starting at 90% idle or above. The report retains first attempts, failures, unscheduled work, per-client and batch p50/nearest-rank p95/max, and per-block volume-minus-overlay deltas. With six pairs a batch p95 is the observed maximum. Sampling occurs locally with zero CI queue. [Workload implementation](../../../../scripts/ci_edit_loop.py)

Use Docker event intervals on the daemon clock, client elapsed time on the host clock and command CPU/wall time within each job. Guest PSI, diskstats sectors, cache inventories, daemon event retrieval, host process I/O and macOS physical-device counters are sampled outside the application timer. Keep per-cgroup `io.stat`, guest vdb sector bytes (also reported as byte deltas), supervisor process bytes, systemwide host device bytes and logical cache-hit bytes separate. ext4 writeback attribution is inode-based and can move between writers. A missing counter, inaccessible device or missing event is unknown. External host writes, sample overhead, shared-inode writeback and work continuing after process exit limit causal attribution. No guest fsync duration trace, current-worker host-device profile or recurring live improvement has yet been demonstrated. [cgroup writeback attribution](https://docs.kernel.org/6.18/admin-guide/cgroup-v2.html#writeback)
