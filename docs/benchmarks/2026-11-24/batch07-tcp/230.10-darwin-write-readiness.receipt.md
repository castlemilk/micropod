**24 November 2026 · 230.10 · Does an unsent-data threshold bound writes on the native relay socket?**

Local/host-only Darwin 25.5.0 arm64. Both arms used the original Micropod socket preparation at `a60d203b16b24abd857e1b5c9e817636b241f850`, which enables nonblocking I/O and TCP_NODELAY. One private IPv4 loopback listener, 524,288-byte sender buffer and two 256 KiB application writes, matching the stock relay chunk. The listener requested an 8 KiB receive buffer and held off application reads until after the offers. The only change set TCP_NOTSENT_LOWAT on the sending socket from its inherited readback of 0 to 16,384 bytes.

| Per connection | Control | 16 KiB threshold |
| --- | ---: | ---: |
| Initially writable by kqueue | 16/16 | 16/16 |
| First 256 KiB write accepted in full | 16/16 | 16/16 |
| Immediately writable by kqueue after first write | 16/16 | 1/16 |
| Unconditional second 256 KiB write accepted in full | 16/16 | 16/16 |
| Verified full 512 KiB, both EOFs and zero sender retransmissions | 16/16 | 16/16 |

Sixteen randomized order-balanced pairs, eight per order, all first attempts preserved. The kernel write event and TCP counters were separate observations. Both arms returned to writable in 16/16 cases after the receiver drained. The receive buffer was free to autotune in both arms. The 15/16 result is a single-host frequency across immediate snapshots. There was no elapsed throughput, fresh p95/p99, CPU/GiB, runnable time or on-wire loss measurement.

Keep stock. The threshold suppressed most write notifications, yet every eager write still entered the socket. The current relay attempts the write first and arms write readiness after a partial or blocked write. A proposed native backlog cap therefore needs explicit application admission or a readiness-gated producer, then verification of actual unsent bytes, delivery and fresh tails. The Linux queued-marker result remains a separate experiment.
