# Fair queueing on the direct published reply path

24 November 2026 · 231.08 · source verification and archived VM interface counters · zero new timed runs or optimization comparisons

**The direct stock worker already requests fair queueing on the service interface.** The earlier four-block VM screen changed the root queue on a bridge-path service's `eth0` from noqueue to fq. On the private direct path the response to the Mac gateway uses `mppub0`. When its root is built-in handle-zero noqueue, the shipping runner requests its replacement with fq. An explicitly configured discipline can survive setup. Treat the earlier +17.7% as evidence for that older bridge-path change. Applying it again as an expected gain for direct stock would double-count the feature. [Earlier VM comparison](../batch06-kernel-queue/service-fq.receipt.md)

Both source revision `7a4eb51a04b51f6332ed49561b3dd0bb42ffacd9`, which contains the qualified direct-path archive, and replay base `ad9d174eda5eb499e0e15675829e21a00d836f84` implement this decision. The direct runner creates a private macvlan child under the publication interface, installs the /32 route to the Mac gateway with Reno and 20 ms minimum RTO, then calls `paceDefaultQueue` on that child. The same helper separately requests fq on the publication NIC if it finds its default root `pfifo_fast`. Each request targets that link's ifindex. Linux 7.3.5 initializes macvlan with IFF_NO_QUEUE. Its private transmit path switches the packet to the lower device and calls `dev_queue_xmit_accel`. The two devices can therefore have separate queue configuration and counters.
