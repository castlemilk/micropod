# Micropod experiments for published TCP under CI load

On Gamma, a single published service beat OrbStack on bulk throughput in 16 of 16 pairs. With 32 services and four concurrent builds, OrbStack led both original batches and all four later file-backed comparisons. The first experiment should send the same traffic through one or 32 host ports to **the same guest service**. This removes a confound in the prepared four-condition benchmark. Splitting traffic among today's 32 services also changes the number of independently scheduled Go processes and CPU quotas. ## What the existing runs can tell us

Each tenant ran with one CPU of bandwidth per 100 ms and `GOMAXPROCS=1`. The latter allows one thread at a time to execute user-level Go code in that process. The stock kernel study captured CPU use for each of the 32 services before and after each client run. The service reads enclose the host timing interval. Dividing each CPU delta by that slightly shorter interval gives an upper bound on the average consumed cores during the interval. Each row contains four Micropod windows. [Archived run plan and source digests](20261124T115609Z-kernel-de4uwit3/plan.json) · [Offline calculation](research_controls.py) · [Go runtime](https://pkg.go.dev/runtime#hdr-Environment_Variables)

| Service condition | Median upper bound for all 32 services, cores | Highest upper bound for any one service in any window, cores |
| --- | ---: | ---: |
| Hot regular file with sendfile | 0.837 | 0.0352 |
| The same file copied in userspace | 1.494 | 0.0726 |
| Memory-backed response | 1.257 | 0.0441 |

The last column rounds the observed upper bounds upward. These values give little support to sustained saturation of individual one-CPU service quotas in the 32-destination case. Short throttles, exhausted ancestor quotas, CPU run-queue delay and network work outside a service cgroup remain plausible. Read `cpu.max`, `cpu.stat` and CPU pressure for the service, build group and each visible ancestor. A leaf's own throttling counters can miss an ancestor exhausting its budget. Record unavailable counters as unknown. ## Tail and transport measurement rules

The client's per-window p99 is the **third-slowest of 240** scheduled requests. Even with independent, continuous observations, the probability that the sample maximum reaches the population p99 is only **91.04%**, from `1 − 0.99^240`. A finite two-sided, distribution-free 95% upper endpoint cannot be recovered from those 240 observed values alone. Report every scheduled arrival and failure. Compare whole paired windows with balanced engine order and retain the current six-second workload. Use a separately labelled longer validation when a decision depends on p99. [Fixed-arrival client](../../../../scripts/netbench/offered/main.go) · [Go HTTP trace events](https://pkg.go.dev/net/http/httptrace#ClientTrace)

The tested host relay is Micropod's C/kqueue implementation. Its profiling already counts pending allocations, copied suffix bytes and blocked writes, and records handoff and connection timing histograms. Those histograms need a per-request join to attribute a tail. Two older lease profiles bounded explicit suffix copies at 0.037% and 0.0124% of forwarded bytes under their respective workloads. Measure that ratio in the 32-service run before designing a new host buffer. Apple’s upstream forwarding implementation and the separate HVF producer answer different questions.
