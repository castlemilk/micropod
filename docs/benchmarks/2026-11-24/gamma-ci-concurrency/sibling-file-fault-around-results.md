# File-backed page faults on Gamma’s CI worker

Keep the **64 KiB default** on the 16 KiB Gamma CI worker. Four fresh holdout boots ran the original Go job and dispatcher. The 1 MiB window shortened Micropod’s eight-build batch by a paired 0.84%, while scheduled HTTP p95 rose by 13.38% and post-dispatch p95 rose by 14.70%. With the default, Micropod won scheduled p95 and p99 in all eight held-out windows, and OrbStack finished seven of the eight build batches first. [Raw stock-workload replay and boot manifests](sibling-file-fault-around-holdout.json)

The experiment changes how many already-resident, file-backed pages Linux may map on a first fault. On the 16 KiB guest kernel, the default 64 KiB window covers four pages and the 1 MiB window covers 64. Both settings used the same signed host binary, guest runner, image, scheduler, quotas and ordinary disk attachment. The temporary bootstrap set the value before containerd started. A second observer read it back after the workload. [Sealed product and embedded kernel configuration](sibling-file-fault-around-product.json)

Each engine ran 64 containers on four vCPUs and 4 GiB. Each of 32 service/client pairs had its own internal network. Eight of the clients simultaneously vetted, tested, compiled, linked and ran two revisions of the Go project. The 32 warmed HTTP clients offered 64,000 requests/s for 1.5 seconds. A scheduled latency includes time waiting to dispatch. Post-dispatch latency starts when the client issues the request. Build time runs from the first job starting until all eight finish.

## The kernel change and actual jobs

After each measured boot, the native worker mapped a warmed, executable-backed 1 MiB region of the same Go binary used by its builds. All 64 file pages were resident and the new mapping initially had zero present page-table entries. With the default window, the first touch mapped four pages and a sweep of the whole region took 16 minor faults. The larger window mapped all 64 on the first touch and the sweep took one. Each setting produced the same result in both access directions and recorded zero major faults in this probe. [Pinned executable, mappings and page-table checks](sibling_file_fault_around_mmap_linux.go)

Across the eight matched instrumented windows, the larger window reduced minor faults in the eight native build trees by 20.98%. The median window went from 394,086 to 311,128. The largest child peak RSS reported for a build rose by a paired 2,800 KiB. Guest-wide available memory after the wave was a paired 40.6 MiB lower. The process counters include anonymous and file-backed faults. Only the separate mapping probe identifies the kind of fault directly. [Resource counters and workload replay](sibling-file-fault-around-results.json)

The instrumented trial used the same Linux child-resource observer on both engines. It held each sample in memory until all builds and HTTP requests in the wave had finished. The later stock trial checked the original mounted scripts in all 16 builders across both engines before and after the run. Its dispatcher included no observer or artificial delay. Each trial reversed the order of the two settings on its second seed, and each boot ran four paired engine windows. OrbStack retained its own 4 KiB guest throughout. A separate 64-container boot recorded the Go 1.26.11 action graph for all 128 test invocations. It completed 768,000 HTTP requests and validated 50,432 timed actions, including 256 compiler commands, 256 linker commands and 128 vet commands. In each of four rounds, the two jobs finishing last on Micropod were matched to the same slots on OrbStack. Their first-revision test command took 17.6 ms longer on average. The two compiler subprocesses took 14.4 ms longer in wall time, the vet subprocess took 15.3 ms longer, and the two linkers together took 14.5 ms less. ## Queued cross-vCPU wakeups during CI

A separate stock-workload boot traced the Linux `csd_queue_cpu` event on all four native vCPUs with `TTWU_QUEUE` enabled. From the first scheduled HTTP request to the last response, the four waves recorded **0, 0, 1 and 0** cross-vCPU queue entries for `sched_ttwu_pending`. From the last response until the last of the eight builds completed, the same waves recorded **1,381, 671, 407 and 580**. Each wave offered 96,000 requests from 32 clients. A pinned membarrier control produced all eight expected callbacks from vCPU 0 to vCPU 3. All five captures reconciled with their per-vCPU ring counts and reported zero lost events. The guest reported a shared L2 cache for its four vCPUs. [Raw captures and positive control](20261125T060757Z-sibling-ttwu-diagnostic-vqra08ch/ttwu-summary.json) · [Independent workload, timing and drive replay](sibling-scheduler-wakeup-diagnostic.json)

The kernel emits one such record per task it queues for remote processing. Several queued tasks can share an interrupt, and a remote wakeup can take a direct path. The trace identifies the context that queued each task. During the build tail, 864 records came from `containerd-shim`, 539 from `containerd`, and 843 from kernel workers on vCPU 0. The HTTP clients also poll their drain file every 10 ms after they finish. The trace establishes timing and leaves the recipient task and cost of each enqueue unresolved. ## Switching the scheduler wakeup queue

Keep `TTWU_QUEUE` enabled for this CI profile. Four further boots compared it with `NO_TTWU_QUEUE`, using the stock jobs, 64 KiB fault window and the same 250 µs scheduler slice. The second seed reversed the boot order. Every guest began with the queue enabled and read back the selected state before and after the workload. All other scheduler feature bits matched. The selection ran after containerd initialized and before job recovery, the Docker API and the measured containers. This trial measured settled CI service. ## Worker drives and baseline

Fresh native arms launched by the standalone Gamma benchmark CLI and the dense CI fixtures use a dedicated 16 GiB APFS sparse image for the 6 GiB configured worker disk. The provisioner creates `.fseventsd/no_log` and `.metadata_never_index`, disables Spotlight on that volume, and checks the actual raw disk and mount identities. After each worker exits it ejects the writable volume, reads its history from a read-only remount, and then ejects and removes the image. The regular CLI’s two- and four-worker preflight used two distinct volume UUIDs. Both read-only remounts reported indexing and searching disabled, with zero FSEvents journal files and zero journal bytes.
