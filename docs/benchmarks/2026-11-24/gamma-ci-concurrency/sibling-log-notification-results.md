# Event-driven container logs on Gamma

Micropod’s native Docker engine now uses a single Linux inotify descriptor to follow the private, RAM-backed CRI logs of its running containers. This follows the change to use containerd task-exit notifications. With 64 quiet containers, the two changes together removed the recurring status requests and log reads. The optimized worker finished the eight-build batch before OrbStack in seven of eight windows and had lower scheduled HTTP p95 and p99 in all eight. OrbStack retained its lead once the client had dispatched the request. ## CI workload

Micropod ran a four-vCPU, 4 GiB Linux worker on Apple Virtualization.framework. Each engine ran 64 containers on 32 private networks. While eight clients vetted, tested, compiled, linked and ran two Go revisions, 32 warmed clients offered 64,000 HTTP requests per second. Two boot pairs reversed the runner order. All four Micropod boots used the same signed host executable, kernel and bootstrap. The host was 88–94% idle immediately before the four boots. Scheduled latency starts when a request is due. The four boots accounted for all 3,072,000 offered requests and 256 two-revision builds with 4,096 workload tests. Matching the same seed and wave, inotify reduced Micropod’s scheduled p95 by a median 11.1%, scheduled p99 by 12.6%, post-dispatch p95 by 7.2%, and build time by 1.33%. Build time improved in both seeds. Scheduled p95 rose 3.0% in the first seed and fell 13.1% in the second. ## Idle cost and output integrity

With task-exit notifications alone, the prior runner still attempted about 314 log drains per second when idle and 317 during builds. In a separate diagnostic, the inotify runner recorded **zero** status calls and **zero** log drains across 5.09 seconds idle and four complete build waves. Its Docker engine recorded zero read syscalls during the idle samples. A foreground container that produced stdout and stderr triggered three measured drains. Eight explicit stats requests triggered eight status calls. The live engine had one descriptor carrying 64 watches before and after the workload. [Kernel counters, positive controls and descriptor counts](sibling-log-notification-rpc-results.json)

On a private worker with 112 simultaneously running containers, two next-exit waiters observed code 43, both live log streams and unterminated final bytes arrived, six concurrent foreground runs returned their expected output and exit codes, and a killed container reported 137. A separate log-heavy check ran eight foreground jobs on each runner. Each job delivered exactly 150,581 bytes on stdout and 150,581 on stderr, including a long split record and a final line without a newline. All 16 stream hashes matched across the two builds, and every wait result agreed with inspection. [112-container lifecycle](20261125T072547Z-sibling-log-notify-2ozemvd7/follow-lifecycle.json) · [Independent byte-for-byte replay](sibling-log-notification-burst-replay.json)

The watcher registers a job’s directory before the first drain and coalesces notifications while output is pending. A rename or lost watch restores the existing polling path for that log. Queue overflow restores polling for the engine. Exit still triggers a final drain. After applying the measured change to the optimization worktree, its own Linux ARM64 test binary passed all 12 focused tests on a fresh Micropod worker. The guest tests checked 112 watches sharing one descriptor and their return to zero. ## Host volumes and cleanup

Every fresh native worker in these Gamma fixtures stores its configured 6 GiB disk on its own 16 GiB APFS image. The host provisioner creates `.fseventsd/no_log` and `.metadata_never_index`, checks the scoped Spotlight status before timing, and checks the same volume again on a read-only remount after worker shutdown. Across the two optimization stages, all 18 new worker volumes reported indexing and searching disabled with zero FSEvents journal files or bytes. All images were ejected and removed. The cumulative audit checked 41 dedicated volumes, 280 retired fixture scopes, and all 24 original baseline files and their preserved copies. [Provisioner](worker_apfs_drive.py) · [Read-only remount and cleanup evidence](sibling-log-notification-release-cleanup.json)

The first inotify diagnostic completed its workload and lifecycle check, then the native Docker API rejected the test launcher's exec environment option. The corrected launcher sets the environment inside the guest shell. A separate preflight attempted to verify the test binary before staging had created it. Moving verification to the staging callback resolved it. The four scored boots completed after these fixes.
