# Native Docker exec, CI checkouts and HVF restores on Gamma

Managed HVF passed five stock Docker exec checks, including output while the process was still running. VZ passed the same five checks in its first qualification, then intermittently missed the detached-start deadline during repeated runs. Under ambient load, Micropod won every pair on a 1,058-file checkout copied into a job and on eight simultaneous builds of the smaller guest helper. OrbStack retained the lead on warm builds of the large checkout over a host bind mount. [Machine-readable results](managed-ci-git-and-exec.json) · [Raw receipts](managed-ci-git-and-exec-receipts.tar.gz) · [Tested source and harnesses](managed-ci-git-and-exec-sources.tar.gz)

The B3 bridge and IPvlan scorecards remain the historical network baseline. The subsequent B4 report already records zero-vmnet egress and multiqueue throughput. The updated B4/B5 plan now directs production work through the managed worker and real Docker clients. This study tests B4.4 workspace behavior, B4.5 CI and resource discovery, and B5 restore behavior at that entry point. ## Docker compatibility

Docker CLI 29.7.2 exercised the managed containerd API through each Mac worker’s own Unix socket. Separate stdout and stderr frames, binary stdin, EOF, PTYs, resize, detached process status, working directories and environment overrides passed on HVF, VZ and the OrbStack reference. Each native worker also passed the existing Compose and Docker restart and events checks, 12 stock archive cases, and the native stop-during-copy case. An in-guest observer ran 26 regression tests and found zero leftover exec FIFOs and containerd tasks after the checks. [Qualifier](../../../scripts/qualify_docker_exec.py) · [Raw receipts](managed-ci-git-and-exec-receipts.tar.gz)

For the plain-output test, the first stdout/stderr observations were 20.018/20.028 ms on HVF, 14.092/14.097 ms on VZ, and 26.304/26.321 ms on OrbStack. The release markers followed at 42.916, 29.711 and 49.279 ms respectively. These are single ordering checks. The older runner produced zero bytes on both streams at the six-second deadline and failed all five groups. Its VMM build also differed. The source-build change routes attached exec through containerd process streams and a PTY when requested. A progressing reader can drain a long-running command. Remaining Docker work includes interactive PID 1 attach and `docker run -it`, per-exec `--user` and `--privileged`, custom detach keys and live network changes. Raw exec inspect reports exit code 0 for a running process on Micropod and null on the reference. Detection of a quiet client disconnect through a half-closing relay can be delayed until output resumes or the process exits. ### Repeated detached execution and event order

On one fresh VZ worker, four of six full stock-client runs timed out at five seconds on `docker exec -d`. The other four test groups passed on every run. Four full runs on HVF passed, and all ten separate Docker and Compose event checks across the two workers passed. A focused detached-start probe then passed eight times on each backend, including four attempts with an open, idle event-replay reader. The timed operation and its five-second limit were the same. A missing probe file after the first repetitions and a command-marker collision in an early probe were harness failures. The raw archive retains these attempts. [Stock-client driver](../../../scripts/qualify_docker_exec.py) · [Per-run and per-command receipts](managed-ci-git-and-exec-receipts.tar.gz)

A guest clock witness on VZ recorded a 671.94 ms backward wall-clock step at 31.584 seconds of monotonic uptime. The host witness stayed stable. The pinned Apple host library requests wall-clock synchronization every 30 seconds. Moby also assigns event timestamps from the wall clock. An earlier VZ event test had rejected decreasing timestamps around this point in guest uptime. It retained no raw event rows, so attribution of that failure remains open. The event qualifier now preserves raw rows and host monotonic arrival times, checks causal lifecycle order, duplicates and bounded replay, and reports backward timestamp steps. [Event qualifier](../../../scripts/qualify_docker_events.py) · [Apple time synchronization](https://github.com/apple/containerization/blob/c0185aea5c04fcd4d1cfe9359e0066a380835403/Sources/Containerization/TimeSyncer.swift) · [Moby event timestamps](https://github.com/moby/moby/blob/master/daemon/events/events.go)

Two further VZ workers alternated the original full qualifier with one that subscribed before launching Docker and immediately read the matching exec-create event. With the original queued-history reader, the VZ workers passed 3/8 and 4/8. With the concurrent reader they passed 8/8 each. Two fresh HVF workers passed 4/4 per reader each. Both readers used the same stock CLI, command and five-second deadline. OrbStack passed the concurrent-reader qualifier. The instrumented workers ended with zero exec tasks and FIFOs. The additional workers used production guest tools without the observer, so those two diagnostic requests timed out. Every stock-client invocation verified removal of its own test container. This identifies a reproducible dependence on the observation pattern. The responsible VZ transport or runtime component remains undetermined. [Driver and host tests](managed-ci-git-and-exec-sources.tar.gz) · [All alternating samples](managed-ci-git-and-exec-receipts.tar.gz)

An intermediate qualifier closed its event socket after reading HTTP headers on both Micropod backends and failed before exercising detached start. The final version retains a descriptor for cancellation while the reader owns the response. Its nine exec tests and the three event tests passed. Separately, a VZ macvlan launch without the pinned kernel selected the default VZ kernel and failed to install the nftables netdev egress chain. That worker never served Docker and required SIGKILL during retirement. Its process group, disk holders, mount and backing image were verified gone. The repeated VZ Docker measurements used the pinned kernel. [Per-attempt boot, teardown and test logs](managed-ci-git-and-exec-receipts.tar.gz)

A final VZ worker recorded containerd task events inside the guest while running six original and two concurrent-reader qualifiers. Seven passed. For the single original-reader timeout, the guest emitted `exec_create` within 23 ms of the host invocation. Immediately after the 5,004.57 ms timeout, the guest could inspect that exact exec ID. It reported PID 0 and `Running: false`. At that point, containerd had seen neither an exec-added nor an exec-started event for it. The corresponding guest-side `exec_start` arrived 5,018–5,064 ms after invocation. The other seven commands had their expected containerd events. This places the observed delay between guest exec creation and its native start. The trace cannot distinguish a delayed start request from a delayed guest handler. [Guest trace and clock calibration](managed-ci-git-and-exec-receipts.tar.gz)

### Main-checkout machine and Micropod CLI

The main checkout at `1db09e63` also exposes a supervised HVF machine through `micropod machine`. On a private machine with its own disk, the source-built supervisor and VMM ran the qualified native guest tools. Stock Docker passed all five exec groups on that socket and copied a file containing NUL and non-UTF-8 bytes into and out of a running container. The original Micropod CLI ran and inspected that same container but rejected detached exec. It returned status 1 for a guest command that exited 23 and discarded its stdout. [Machine driver](../../../Sources/MicropodRuntime/HVF/HVFMachineClient.swift) · [Baseline receipts](managed-ci-git-and-exec-receipts.tar.gz)

The corrected Micropod CLI returns the actual exit status and keeps stdout and stderr separate for noninteractive text commands. Successful detached exec requests no attached streams and returns when the engine acknowledges start. It propagates daemon start errors and rejects an unexpected attached-stream response. On the same running machine, the previous status-23 command preserved its exit and exact text on both streams. Empty output and trailing newlines matched stock Docker. A detached command returned silently in 17.47 ms, remained running until released, and then exited 39. An immediately exiting command returned 0 to the launching client and 71 in Engine inspect. A missing working directory returned a client error. Both clients removed their own containers. The isolated Swift build added only the exec change to the baseline revision. The supervisor and VMM remained the same for both clients. [CLI](../../../Sources/MicropodCLI/ContainerCommands.swift) · [Docker adapter](../../../Sources/MicropodRuntime/Engines/DockerEngine.swift) · [Compared command receipts](managed-ci-git-and-exec-receipts.tar.gz)

The build tested here collected ordinary exec as text. The subsequent release CLI streams binary input and output on the same public interface. Native terminal exec, copy and export remain open on this backend. [Subsequent core CLI qualification](../2026-11-26/mounted-ci-gamma.md) The stock Docker client has separately verified byte-stream and archive support. All 72 selected outer Swift tests passed. The five exec response tests also passed against the current checkout with its concurrent runtime ownership changes. The installed Micropod 0.13.3 app and this staged source build have different hashes. The test machine shut down with an orderly guest poweroff, released its lock and socket, and left the default runtime configuration and original disk intact. ## Git metadata and host edits

A Darwin-authored read-only Git index caused the Linux client to rescan the contents of all 1,058 tracked files on both engines. With a guest-refreshed private index or a warmed guest-created writable clone of the tree on the same host share, Git Trace2 recorded zero full-file refresh scans. On the second metadata build, median warm Git status took 125.08, 28.75 and 31.37 ms on HVF across these three layouts. OrbStack took 52.74, 9.16 and 11.56 ms. Six alternating pairs per layout checked both Git status and actual file bytes after same-size host edits. The three fully recorded runs passed all 216 engine observations. An earlier prototype reported a visibility mismatch and stopped before recording the affected engine and file digest. The diagnostic now preserves both and retries the observation after 250 ms. [Topology driver](../../../scripts/bench_workspace_git.py) · [Trace and sample receipts](managed-ci-git-and-exec-receipts.tar.gz) · [Git index refresh](https://git-scm.com/docs/git-update-index)

In the measured Rust VirtioFS build, the handler borrows the request name, reuses the lookup path and avoids redundant inode-map work. A host-only replay of the same 1,058 lookups measured 3,174 allocations or reallocations on the previous handler and zero on the updated one. Median scan time fell from 2.670 to 2.258 ms, with a median paired reduction of 14.4% over 12 wins in 12 pairs. A guest ftrace of a warm writable host-mounted clone recorded 1,366 completed LOOKUP, 25 OPEN and 26 READ operations. Of the LOOKUP completions, 1,362 also had a paired virtiofs workqueue event. The large host-mounted warm build remained slower than OrbStack across the baseline, candidate, candidate and baseline worker sequence. This replay gain has yet to produce a repeatable end-to-end checkout gain. [Paired host replay, guest traces and alternating builds](managed-ci-git-and-exec-receipts.tar.gz)

A separate two-process APFS test observed all 37 expected page contents. Twelve pairs had identical device, inode, size, modification time and change time but different bytes while a writable mapping existed. On one reopen the generation was valid, then another process changed the page before the first read. Keeping a mutable file’s previous guest pages based solely on its host stamp can therefore return stale data. The candidate retains per-request host metadata validation. The APFS test used the protected fixture drive. ## HVF snapshot and production boundaries

The frozen integrated VMM restored five successive workers. From VMM spawn to Docker ping, the median was 13.98 ms (12.99–15.90 ms). The median first container finished in 157.21 ms. Eight parallel forks all finished their first container by 409.43 ms. The probe verified separate CoW disks, private writes, a delayed fresh restore and 15 clean VMM exits. Snapshot capture took 233.32 ms. The first-container result exceeds the plan’s 100 ms target. [Direct fork measurements](managed-ci-git-and-exec.json) · [B3 scorecards](phase-b3-results.md) · [B4/B5 acceptance criteria](../../research/2026-11-25-phase-b4-plan.md)

Two simultaneous restores through the original managed CLI each launched a distinct VMM, Unix endpoints and writable disk cloned on the same APFS volume. Containers with identical names made separate rootfs, volume and physical workspace writes. Both forks nevertheless reported the template’s worker, instance and Linux boot IDs. Docker rejected the configured per-fork workspace path with exit 125 and admitted the path retained by the template. That retained path exposed the fork’s own host directory, so data stayed physically isolated while the client-facing path and identity were wrong. In the final repeat both managed sessions became ready by 168.425 ms, and all three jobs, supervisors and VMMs exited zero. An earlier repeat reached readiness by 53.118 ms. These are individual lifecycle observations with different host load. [Managed fork receipts and earlier fixture failures](managed-ci-git-and-exec-receipts.tar.gz)

The corrected Swift worker compares the schema-1 snapshot’s recorded workspace byte-for-byte with the requested canonical path and checks the live guest’s workspace attestation. It validates the completion marker, VM state file, RAM length, ext4 geometry, and actual disk length when present. It requires an absent destination disk before restoring, so frozen RAM cannot be attached to a previously used worker disk. Capture claims its generation before issuing the trigger and preserves an existing snapshot. A mismatched and an omitted workspace failed in 25.217 and 20.039 ms respectively, with no worker manifest, target disk, session or socket. A fresh-disk restore at the captured workspace reached managed readiness in 212.602 ms, ran the stock Docker file check, and preserved the original disk digest. Both successful workers and their jobs exited zero. The 26 focused Swift tests passed. [Managed worker implementation](../../../Sources/MicropodRuntime/HVFWorker.swift) · [Host and guest qualification](managed-ci-git-and-exec-receipts.tar.gz) · [ext4 superblock layout](https://docs.kernel.org/filesystems/ext4/super.html)

A schema-1 restore resumes the same guest identity. CI jobs that require independent worker identities need independently provisioned workers or independently captured templates. A general per-job fork still needs a guest-side identity and workspace handoff. A clean signed distribution, PID 1 interactive attach, wider network/API conformance and a long multi-job soak remain open. Changes in the separate outer Rust checkout are pinned by content hash. The source archive also includes the original and guarded Swift source, the Go runner, the vendored workload and the exact benchmark drivers. [Source archive](managed-ci-git-and-exec-sources.tar.gz)

## Benchmark integrity

The baseline from `20261124T090510Z-local-d0y_1j57` completed at 6,573.34 MiB/s. The original, separately preserved copy and published qualified binaries all have SHA-256 manifests. This study built its own guest tools and ran its Docker clients against explicit private endpoints. The private OrbStack image tag and builder were removed. [Original baseline and controlled comparisons](../2026-11-24/gamma-qos-and-workers/results.md) · [Preservation manifest](../2026-11-24/disposable-local-fixture/20261124T101312Z-local-iad8j2_g/preserved/manifest.json)

Three early worker retirements exceeded the five-second disk-holder query. A second inspection found the owners had stopped and the disks had no open handles. The three empty `lsof` results took 12.24–15.88 seconds under ambient load. After verifying the disk and volume identities, each drive was remounted read-only, detached and removed. Their original supervisor exit codes were unavailable. The retirement code now gives a slow holder query the remaining time within the existing shutdown deadline. Another VZ attempt rolled back during APFS provisioning before a worker existed. [Retirement code](../../../scripts/bench_engine_tuning.py) · [Cleanup evidence](managed-ci-git-and-exec-receipts.tar.gz)

All 32 disposable APFS volumes, including the source-staging volume, retained disabled Spotlight indexing, `.metadata_never_index` and `.fseventsd/no_log`. Read-only remounts found zero FSEvents journal files and bytes on all 32. No owned disk image remained attached, and all backing images were gone. At completion the 24 original baseline files and their 24 preserved copies matched the manifest. Both qualified binaries and all 37 qualified tool files retained their original hashes. The source archive contains 2,179 entries and the raw archive contains 429 entries, with individual SHA-256 manifests.
