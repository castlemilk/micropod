# Existing implementation and source evidence

**Audit date:** 2026-11-19. **Default branch:** `master`. **Pinned source:** `54980012eb47b458a7f7e1def616d3fa95c970a2` (commit “appcast: v0.13.9 qualification policy”). Read-only audit of the recursive tree and selected implementation, documentation, and tests. No Mac runtime, benchmark, or test suite was executed. “Implemented” below means visible in source, not independently qualified on hardware.

## Decision

Micropod is an existing native Swift container product with Apple Containerization integration, an independently implemented in-process sandbox microVM engine, an external Docker engine adapter, a Docker-compatible API shim, Kubernetes management, APFS volume clones, bidirectional SharedFS view synchronization, and release/runtime lifecycle machinery. A roadmap starting by creating a VM interface, vfkit prototype, Swift VZ backend, Unix Docker socket, basic mounts, port forwarding, and machine CLI repeats substantial existing work.

The OrbStack-style **single kernel hosting Docker and multiple system distributions is not the present architecture**. It should be a separately selected and benchmarked engine/trust profile behind existing runtime interfaces, if its measured memory or density advantage warrants the complexity. Do not replace the current per-container/per-sandbox VM isolation by implication. Likewise, the managed runtime under a dedicated macOS account and a Linux VM isolation boundary are different concepts.

## Core platform follow-up

The follow-up audit rechecked `master` at the same pinned commit. Its implementation priority is the complete build/runtime/cache platform described in [Core container platform](core-container-platform.md), with Kubernetes as a downstream consumer. The original evidence index and issue crosswalk below remain useful foundations; source presence does not establish Docker/Buildx compatibility, OCI/runc equivalence, filesystem correctness or a performance advantage.

| Area | Additional source findings and required work |
|---|---|

Context identity must cover effective source metadata and ordering; source transfer, frontend options, credentials, exporters, cancellation, cache import/export and real prune behavior need end-to-end qualification. | [Runtime equivalence](runtime-compatibility.md) | The Docker schema is a subset. | [Cache and filesystem](cache-and-filesystem.md) | A successful per-file `clonefile` falls through into a data read/rewrite. Chunk ingestion can suppress a write error and return partial hashes; reads do not verify the requested content digest. Context insertion and eviction use different byte bases. Repair these paths, then add durable owner references, coherent metadata/invalidation and measured reuse across the existing stores. |

The detailed sibling audits contain pinned source locations and proposed acceptance fixtures. Their findings are from inspection; no native Mac workload or new conformance/performance test was executed. Known required fields that are unsupported remain release blockers, even if the implementation reports that limitation honestly. Unknown Docker extension keys follow the selected API's compatibility rules rather than an indiscriminate rejection policy.

Upstream runc/containerd inside an explicitly scoped Linux VM is a practical full-semantics path. Its trust domain can be one CI job, project or trusted local environment; it does not depend on implementing the multi-distribution supervisor in #154 or changing the isolated-VM default. Linux host namespace behavior refers to that Linux execution domain, not macOS. Compare Docker API behavior, OCI runtime semantics, runc CLI/extensions and containerd task/shim behavior as separate contracts.

## Remaining network work that should not be lost in renumbering

The original research NET-002 Linux unified bridge/IPAM is a new shared-engine coordination problem, though current sandbox/subnet allocation is implemented. Original NET-004 TCP/UDP forwarder maps to extending #174, not building all forwarding from scratch. Original NET-006 host-resolver DNS/VPN bridge and NET-007 lifecycle local domains remain distinct from current guest hosts files. Original NET-008 direct host-reachable IPs needs an engine-specific capability matrix because the existing vmnet design already assigns guests addresses; do not assume a brand new packet stack. Original NET-009 macOS HTTP/HTTPS/SOCKS/NO_PROXY propagation is separate from the sandbox explicit egress/secrets proxy. Original TLS local development HTTPS is separate from `SandboxCA`, which exists for outbound secret-substitution TLS. Custom high-throughput network code remains gated on profiles proving the host path is limiting a real workload.

## Filesystem findings needing concrete action

1. `FSEventsWatcher` supplies only paths and discards flags/event IDs. A robust implementation needs an explicit lost-events/rescan/start-failure contract. The source proves omitted metadata, not that a particular reported production failure has this cause.
2. `SharedViewSync` protects against old-event echoes with exchanged content hashes and staged snapshot hashes, and tests cover several delayed-echo races. That is valuable existing work.
3. Its full-tree enumeration excludes dot basenames and non-regular files. A direct event for a dotfile can take a different path than a directory rescan; this must be tested rather than described as universally ignoring all dotfiles. Metadata-only changes have the same content hash, so cache coherency must include more than file bytes if POSIX-like semantics are required.
4. A directory event enumerates the entire origin tree before prefix-filtering. This is a plausible high-file-count cost to profile after correctness, not an established bottleneck.
5. `guest/watch.go` already provides guest inotify streaming with recursive watch management. This does not establish host-originated VirtioFS updates generate equivalent inotify events; validate that cross-boundary behavior explicitly.

## Benchmarks: extend the existing harness; do not claim a win yet

`bench_runtimes.py` already warm-ups and interleaves boot/job runs, accepts a current Docker context (so OrbStack can be selected as the Docker endpoint), and compares API/CLI/native/sandbox/machine paths. It has one retry for transient failure, which must become a recorded first-attempt outcome for reliability comparisons. Report samples, failures and retries together. Its machine case changes image/init assumptions, so results must declare the image and isolation boundary, not merely label both as “container”.

`bench_shim_vs_docker.py` collects p50/p95/min/max, serial lifecycle phases and a concurrent batch. It uses a 20% p50 regression rule. That is useful existing infrastructure, but it lacks a complete versioned environment/thermal/background load manifest, robust repeated-batch statistics, randomized cross-runtime ordering, and agreed comparability/SLAs across isolation modes. A single concurrent wall time is not a p50 distribution of repeated concurrent batches, despite its storage label. Stop timeouts are workload semantics and can dominate a misleading aggregate.

Keep native ARM and translated amd64 cohorts separate. Keep cold runtime start, cached image launch, image pull/unpack, first build and warm build distinct. Measure process-start readiness, HTTP readiness and application work separately. Include latency tails/failure rates, steady idle CPU/wakeups/energy, physical memory under 1/10/50/100 equivalent workloads, fsync durability settings, and network throughput/tail latency. A shared-kernel engine may win density while isolated microVMs win a security property; record that tradeoff alongside the result.

`docs/performance.md` is historical measurement evidence, not a current same-host OrbStack result. Parts are stale: it still identifies CLI startup as future work after native XPC already exists. README also contains qualification and older runtime caveats that should be reconciled against current code, completed issue #89 and the current release receipt. Do not turn historical medians or source-level optimizations into a performance claim for an unmeasured current build.
