## Isolating the 32-port CI throughput gap

The single-service holdout and the 64-container CI comparison changed both traffic distribution and background work. The runnable study keeps the job creation barrier before network timing. All 32 services stay resident in every condition. Send the same 32 bulk streams and 40 fresh requests/s through the published listener of one service or distribute them evenly across all 32. Use an equal total CPU and memory budget, the same image and payload, and a fixed four-build admission limit in the churn conditions. [Mixed CI measurements](../benchmarks/2026-11-24/gamma-ci-concurrency/results.md) · [Single-service control](../benchmarks/2026-11-24/gamma-local-peer/results.md) The 23:11 AEDT collection stopped before any timed client because the host denied this session access to OrbStack’s socket. | --- | --- | --- |
| One of 32 resident services | Reference for one busy port with the resident footprint held fixed | Incremental cost of CI on one busy port |
| All 32 resident services | Incremental cost of spreading the same traffic | Combined workload and the additional cost when both factors change |

Balance condition and engine order across blocks. Report receiver MiB/s, each stream’s share, scheduled fresh p95/p99, request failures and reconnects. Record jobs/s, release-to-last-job time and runnable wait over the same windows. Compare the churn-on versus churn-off difference at each traffic distribution with paired uncertainty. A larger churn effect only when spread across ports would justify profiling listener wakeups and per-service scheduling together. The four-block profile verifies the invoked service identities and actual receiver port count. Each service has a one-CPU quota. Distribution across 32 services can also change available service CPU within the fixed four-vCPU VM. [CI service fanout and kernel measurements](../benchmarks/2026-11-24/gamma-ci-concurrency/fanout.md)

A pair of fresh eight-build runs enabled Linux receive flow steering on the private virtio queue. Micropod's file throughput rose 1.9% against its matched control. Memory throughput fell 3.4% and fresh p95 rose in all eight comparisons. The final block overlapped a Mac build. Across the first three blocks the file and memory changes were +1.3% and −3.8%. The service cgroups recorded zero throttling periods across both engines. [Private queue, service CPU and paired measurements](../benchmarks/2026-11-24/gamma-ci-concurrency/published-link-results.md#matching-receive-flows-to-the-service-cpu)

Spreading 32 services evenly across the four guest CPUs improved paired Micropod file throughput by 2.8% in all four blocks. Micropod led the matched OrbStack file workload by 1.0% and its memory workload by 17.5%. Its own slowest memory stream lost 22.2% against unpinned service threads. In all eight Micropod windows the slowest service shared vCPU 3 with the publication interrupt. Restricting the private receive mask to vCPUs 2–3 cut memory throughput 24.2% against the off-IRQ control. ## Decision criteria

The original four-vCPU bulk planning range was 4,100–4,600 MiB/s. The 24 November four-vCPU holdout exceeded it. For a new product comparison, keep a balanced 16-pair holdout, retain every attempted round, require at least 15 common clean pairs, zero Micropod fresh losses or bulk reopens, p95 ≤75 ms in each Micropod round and a lower 95% paired throughput bound above parity. For a latency candidate, the proposed screen is lower paired p95, no p99 regression, clean delivery and at least 98% of the selected Micropod control throughput. Record CPU/GiB and runnable wait at the stated process and timing scope. The independent idle CPU target remains <0.1%. [Holdout and latency criteria](2026-11-24-published-tcp-priorities.md)

Use the allocation and admission evidence for the specific scored session on Gamma. The archived 23 November shared-run gate and the 24 November private fixture used different observation scopes. Preserve the role, routes, service, VM limits, admission samples, all first attempts and cleanup for each comparison. [Holdout audit](../benchmarks/2026-11-24/standard-peer-and-read-size/peer-audit.json)
